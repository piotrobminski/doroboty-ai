# Prototype data boundary

The teaching prototype authenticates prepared synthetic accounts using a local SQLite-backed API. Server sessions enforce role and ownership; the operator can access the full scenario. Initial shared `Test1234` credentials are intended for teaching. No real CVs/private material belong here, and this change does not establish production readiness, registration, password recovery or deployment.

`server/database.ts` uses individually salted scrypt (N=32768, r=8, p=3), random 256-bit session tokens and SHA-256 token digests at rest. Sessions expire after 12 hours and are revoked on logout; login rotates the current token. Cookies are HttpOnly/SameSite=Strict/Path=/; set AUTH_SECURE_COOKIE=1 when using HTTPS. State responses use no-store. POST requires an application-specific header, JSON content and matching Origin when present; no cross-origin credentials/CORS support is enabled. Login failures are bounded per socket address, and concurrent derivations are capped. Payloads are capped at 2 MB. Credentials and free text are never logged.

SQLite lives in ignored `.data/` (private directory permissions) or DATABASE_PATH. A middleware guard in dev/preview and Vite filesystem denies prevent direct HTTP access to database/WAL files, including custom database paths and /@fs requests. Do not commit/distribute runtime databases, WAL files, migration backups or session material. Scenario exports exclude credentials/sessions. They are operator-only and include application/CV snapshots and recruiter notes. Full backup/restore requires stopping the server and preserving the SQLite directory. A public deployment would also need HTTPS, individual credentials, recovery/account lifecycle and an independent security review.

GET /api/state projects records according to the authenticated identity. Public views receive published offers; candidates receive their own applications/drafts/saved jobs without recruiter notes; employers receive their company’s submitted snapshots, without current candidate full profiles or legacy private notes. Client-supplied identity changes are rejected. Mutations use complete server state, shared Zod validation and domain ownership/transition checks inside a transaction. Relational foreign keys and composite job/company references reject broken ownership links; unique candidate/job keys prevent duplicate applications. SQL update guards keep submitted payloads and existing history immutable, while ordered event inserts derive the current stage. Only authorized full-scenario import/reset replaces rows. Schema-version migration creates a private mode-0600 SQLite backup and atomically verifies lossless JSON reconstruction before removing the old JSON store; it never rewrites account/session rows or silently reseeds a damaged database. Imported text is rendered through React; import rejects unknown versions, duplicate IDs, broken references, oversized data and removal/reassignment of existing accounts. Legacy localStorage is never automatically trusted as authenticated identity or migrated.

The employer-only competency evidence hint remains computed locally from submitted criterion/response snapshots. It does not send candidate text/CVs to a provider, fetch material links, log free text, rank people or mutate decisions. Human review remains required.

Implementation references: [Node 24 SQLite](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html), [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [OWASP sessions](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). Actual test evidence is recorded in [the task](tasks/database-auth.md).

## Local OpenAI gateway

OPENAI_API_KEY is read only by the optional Node middleware in Vite dev/preview. Keep it in an untracked `.env.local` or process environment; never use VITE_* for a secret. Participant packaging uses an explicit allowlist that includes `.env.example` but excludes `.env.local`; the client build imports no server module or credential configuration.

The endpoint requires a loopback socket, local Host and matching Origin for POST. It accepts only validated recruiter job-text requests, caps payload/output/concurrency/rate/time and exposes fixed errors without raw upstream details. It does not accept candidate state/CVs or browser-provided credentials, model URLs or arbitrary provider prompts. There is no automatic retry, telemetry or free-text server logging. The Responses request sets store:false; the local server does not persist prompts/results. Provider processing policies still apply.

The current guided form never calls this endpoint, even with a configured key; proposals run locally. Any future provider reconnection requires an explicit transfer disclosure in the UI. Responses are untrusted proposals parsed with shared schemas and rendered as React text; human editing/approval remains mandatory. The local gateway is not an authenticated public API: a deployed integration would require its own server, secret configuration and access controls. Plain static hosting contains no key or working provider endpoint.
